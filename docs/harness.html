◆ Orientation

What the harness actually does

You describe a feature. It writes the product framing, the architecture, the UX structure and the code — then commits each vertical slice on its own branch and hands you a list of the judgement calls it had to make alone.

Two ideas do all the work, and they are worth naming before anything else, because everything in the run is one of them.

  • The graph. The run is a fixed, declared set of steps with edges between them. Nothing decides at runtime what happens next; the edges do. A step starts the moment its predecessors have settled, and a step never re-opens an earlier one.
  • The loop. Every step is itself a small contest: one agent makes the artifact, one or more independent agents are told to refute it, and the step passes only if the harshest of them scores it above the bar with nothing serious outstanding. Otherwise it goes round again with the defects in hand.

The graph decides what runs and when. The loop decides whether the thing it produced is good enough to pass on. Everything else — worktrees, branches, arbiters, the report — is plumbing around those two.

◆ Mechanism · one

The graph: five steps, no back-edges

Every step is a row of data — who makes it, who checks it, how many rounds it gets, what it must produce, when it may be skipped, and which steps come next. The executor reads that table, works out each step's predecessors from the next lists, and starts anything whose predecessors have settled. It names no step by hand, which is why adding one changes no code in the executor.

What "settled" means for the steps downstream

A step that hard-fails, crashes, or is dropped for want of budget blocks everything after it: if po dies the graph is over, and if architect dies build is skipped. A step skipped by its gate is different — a feature with no screens is not a failure, so ux being gated off blocks nothing.

There are no back-edges anywhere. When the architect thinks the product owner queued the slices wrong, it does not edit the issues and it does not declare a different dependency graph in its own document. It files the disagreement and a human-verify row naming the file to amend. Two artifacts of one run asserting different graphs, with only one of them executable, is the failure this rule exists to prevent.

◆ Mechanism · two

The loop: make, refute, score, repeat

Every step in the graph has the same body. One implementation runs all of them, and the only things that vary are which personas fill the roles, which rubric is used, and how many rounds there are — two at the document steps, five attempts per slice at build.

Why the minimum, and why the checkers cannot see each other

Each checker scores a fixed rubric of five criteria, each one anchored at 0.0, 0.5 and 1.0, and the engine — not the checker — multiplies those by the weights. A total the checker asserts for itself is ignored, and a criterion it did not score counts as zero. Across checkers the step takes the minimum: an adversarial panel is only as green as its harshest lens. Checkers in a round run at the same time and no prompt contains another's verdict, so agreement between them is evidence rather than an echo.

Silence is never approval

An agent that never answered is retried once for free, because a dropped connection is not a mistake worth recording. If the retry also fails the round is spent and marked errored rather than rejected, and the defect is filed against the harness so no maker is ever handed "you returned nothing" as work to repair. A round in which a scoring checker failed to report scores zero, never a vacuous one.

The rubrics

StepBarRoundsWhat the checker weighs
po0.802Gherkin quality 0.30 · INVEST vertical slices 0.25 · every seed decision landed 0.15 · the seed's own vocabulary 0.15 · mockup matches the happy paths 0.15
architect0.802boundaries and invariants 0.30 · the test seam named per slice 0.25 · ADR completeness 0.20 · fit with the existing code 0.15 · each slice buildable in one sitting 0.10
ux0.802state matrix per screen 0.30 · flows and recovery 0.25 · structural WCAG AA 0.20 · information architecture 0.15 · extends the mockup in place 0.10
build0.805Clean Code 0.30 · DDD in the code 0.25 · idiomatic for your stack 0.20 · tests assert behaviour 0.15 · no duplication or dead code 0.10 — plus a separate binary tester that is never averaged in

At the document steps only a critical defect can veto a passing score. At build, high vetoes too, because that is where the checker has executable ground truth behind it.

◆ Mechanism · three

Where the two compose: one graph step, many loops

build is a single node in the graph, and inside it the loop runs once per slice — concurrently, when the slices do not depend on each other. This is the whole design in one place: the graph says build comes after architect, and the loop says this slice is not done until a green suite and a code review both agree.

The one config line that changes the shape of the run

Parallel lanes open only when your project declares commands.install. A fresh worktree has no installed dependencies, so without that command the test suite cannot run there and the engine stays sequential — and says in the log that it did, and why. Give it whatever makes a freshly-checked-out tree testable: npm ci, ./mvnw -q dependency:go-offline, uv sync.

◆ Setup · one

Install

macOS, and Windows under WSL:

curl -fsSL https://raw.githubusercontent.com/rcforte/sdlc2/main/install.sh | bash

Windows, native PowerShell:

irm https://raw.githubusercontent.com/rcforte/sdlc2/main/install.ps1 | iex

Either script installs through Claude Code's own plugin CLI and then checks that the host actually registered the nine personas and four skills — the most likely thing to go wrong on a first install. Re-running is safe: it updates and re-checks, so it is also the repair path. Restart Claude Code afterwards.

By hand, it is two commands:

claude plugin marketplace add rcforte/sdlc2
claude plugin install sdlc2@sdlc2-marketplace --scope user
TaskCommand
Updatere-run the installer, or claude plugin update sdlc2
Repair or diagnosere-run the installer — it re-checks the inventory
Uninstallclaude plugin uninstall sdlc2@sdlc2-marketplace, then claude plugin marketplace remove sdlc2-marketplace
Work on sdlc2 itselfclaude plugin marketplace add ~/dev/code/sdlc2 — your clone becomes the installed plugin

Use the qualified id sdlc2@sdlc2-marketplace throughout. claude plugin details accepts the bare name but claude plugin update answers Plugin "sdlc2" not found.

Restart, or you will measure the wrong engine

A Claude Code session fixes its plugin directory when it starts, and the cache keeps every installed version side by side. After a mid-session update the old path keeps resolving and keeps working — silently. Two early runs of this plugin, about 6.3 million agent tokens, executed 0.1.1 while 0.1.2 was the installed version. The run now prints which engine it is on its first line, and refuses to start from a superseded one.

◆ Setup · two

What your project must already have

sdlc2 builds features into an existing project. It cannot create one, because it refuses to start until your test command is green. Before the first run:

  1. A git repository, and a clean tree. git status --porcelain must be empty. Slices commit; stray changes would be swept into them.
  2. Your session rooted at that repository. There is no repoRoot argument — subagents inherit the session's directory. A session started elsewhere will cut slice/* branches and write .sdlc2/ into that repo instead, plausibly and silently. A cd in a shell command does not fix it.
  3. A resolvable default branch. Every slice branch is cut from it.
  4. A green test suite. The command in your config is run once before the graph starts. A red baseline makes every later verdict meaningless.
  5. An ignore rule for your harness's own worktrees — commonly .claude/worktrees/. Those are created inside the repository; an un-ignored one shows as untracked and fails the clean-tree check. sdlc2's own slice worktrees need no rule, because they live outside the repo.
  6. A writable parent directory, since ../.sdlc2-worktrees/ is created there. A stale one from an aborted run is harmless — every run stamps its own container.

◆ Setup · three

The config block — the only configuration there is

It lives in your project's own CLAUDE.md, inside a fenced YAML block delimited by an HTML comment. There is no second config file to drift against. The first run proposes the block, shows it to you, and asks before writing — that file is yours and it loads into every session.

## sdlc2
<!-- sdlc2:config -->
```yaml
stack:  "Java 21, Spring Boot 3, JUnit 5"   # what the reviewer judges idiom against
lanes:  4                                    # optional; max slices at once. Default 4
commands:
  test:    "./mvnw -q test"                 # MANDATORY — the tester's only oracle
  install: "./mvnw -q dependency:go-offline" # optional; UNLOCKS PARALLEL LANES
  build:   ""                               # optional; omit what the stack lacks
  run:     ""
  e2e:     ""
seam:
  backend:  "REST via MockMvc (@SpringBootTest)"
  frontend: ""                              # empty until a frontend exists
```
<!-- /sdlc2:config -->
FieldRequiredWhat actually reads it
commands.testYesThe tester, on every attempt, and the baseline check before the graph starts. Absent or empty and the run refuses — twice, once before the engine and once inside it.
stackStrongly advisedPut in front of every persona. sdlc2 has no house stack; this line is what the developer writes in and what the reviewer judges idiom against.
commands.installNoThe lane gate. Present → independent slices build concurrently in their own worktrees. Absent → strictly sequential.
lanesNoThe concurrency cap. Default 4. Root-level only — it is not merged per directory.
seam.backend / seam.frontendNoHow an acceptance test is driven here. The architect names the seam per slice; this is the house style it starts from.
commands.build · run · e2eNoHanded to the developer and the tester where the stack has them. Omit what does not exist.

A CLAUDE.md nested in a subdirectory overrides the root block for slices whose files live under it, longest matching path wins. That is how a monorepo gets per-area commands without a separate context map: a ui/CLAUDE.md declaring npm test next to a root declaring mvn verify.

Make sure your test command really tests

The tester runs your declared command and reads its output. A suite that quietly skips its integration tests — a container flag that disables them without Docker, a fixture excluded from the runner — is indistinguishable from a real pass, and no rubric will ask. Choose the command that fails when the feature is broken, not the one that is fastest to go green.

◆ Product → Design → Build → Report

Running it

/sdlc2 new-feature "guest checkout"   # the whole graph
/sdlc2 status                         # features, verdicts, open rows, branches
/sdlc2 help

The first run in a repo is interactive, briefly

Two things happen in the conversation before anything autonomous starts, and they happen there for a structural reason: a workflow's subagents have no channel back to you, so a workflow can never interview.

  1. It grills you, if there is no seed yet, and writes the shared understanding to .sdlc2/features/<slug>/feature.md under six headings: capability, agreed scope, out of scope, decisions, ubiquitous language, open questions. The product-owner step is scored on covering every one of them, so a thin seed shows up two steps later as a low score.
  2. It proposes the config block and asks before appending it to your CLAUDE.md.

After that the graph runs to the end unattended. Watch the log if you like: every round prints its round number, its score against the bar, its defect count, and whether a veto or a red suite stopped it.

What lands in your repo

.sdlc2/features/<slug>/
  feature.md              the grilled seed, extended by the product owner
  mockup.html             happy paths from po, state variants added by ux — ONE file
  design.md               domain model, boundaries, the seam per slice
  issues/NN-slug.md       one vertical slice each, with Gherkin and Blocked by:
  VERIFY-WITH-HUMAN.md    every call an arbiter made for you — append-only
  runs/<runId>.md         node table · slice table · open rows
docs/adr/NNNN-*.md        architecture decisions
slice/<feature>/NN-slug   one branch per slice
sdlc2/<feature>           the paperwork commit, cut from your default branch

The run report is written under every outcome, including a graph that aborted. If it is missing, the workflow never started — bad arguments or a missing test command — and the error text says which.

◆ After the run

Reading the result

Each step reports a verdict, a score and the rounds it consumed.

VerdictWhat it means
passCleared the bar with nothing serious open, inside its rounds. No human owes it anything.
soft-passThe rounds ran out and an arbiter decided. There is a decision record waiting for you. A run with a soft-pass is never reported as clean.
partialbuild only: some slices shipped, some did not.
hard-failThe step could not produce a judgeable artifact, a checker could not judge it at all, or a red suite survived the last round. Everything downstream is skipped.
skippedA gate did not fire, an upstream step did not pass, or the budget ran low. The reason is printed.
not-runNever became ready — that means the graph edges are wrong, and it is a bug, not an outcome.

Why a slice was escalated

These four reasons are deliberately distinct, and each names what the last attempt actually ended in. A slice that never compiled is never reported as a failing test suite.

ReasonWhat happenedWhat you do
no-commitThe developer never reached a green commit.Nothing to review — there is no branch. Read the defects and re-cut the slice smaller.
tester-redIt committed, and the suite stayed red.The branch exists and is broken. The defects say how.
tester-silentThe tester never answered.The slice is unverified, which is not the same as broken. Run the suite yourself.
unjudgeableA checker reported it could not judge the slice at all.Usually a missing seam or an ambiguous acceptance criterion. Read the checker's note.
arbiter-rejectedTests were green but the arbiter judged the surviving craft findings too serious to accept.The branch is real and passing. Decide the debt yourself.

The human-verify file

VERIFY-WITH-HUMAN.md is append-only, and every arbiter decision leaves one index row and one record: the issue, the options, the decision, the rationale, the risk if it is wrong, what would change its mind, and the defects that were still open. Ids are namespaced per step so two concurrent arbiters cannot collide. This file is the run's real output for you — the branches are what it built, this is what it had to decide without you.

◆ Yours

Merging

sdlc2 never merges to your default branch and never moves it. Reviewing and merging is the part it deliberately does not do.

  • Merge in slice order. A slice with Blocked by: is cut from its blocker's branch, so merging it merges the blocker too. The report says which slices were stacked.
  • The shipped sha is the sha a tester passed. The arbiter is not allowed to commit, so nothing was touched between the green suite and the branch you are merging.
  • The paperwork is on sdlc2/<feature>, cut from your default branch, and HEAD is left there so the tree is clean and the next run is not blocked. If the report carries a Paperwork not committed section, that step failed and the artifacts are still untracked.

◆ Reference

The rules that never bend

  • A red suite is not arbitrable. No score, no deadline and no arbiter commits over it.
  • The arbiter never commits. A green verdict from before the arbiter touched the branch is not evidence about the branch after.
  • Silence is never approval. A missing verdict is a critical defect, and a checker that passes the work while filing a critical defect against it is resolved as a fail.
  • No back-edges. A later step never re-opens an earlier one; disagreement becomes a human-verify row.
  • Every round is a new agent. Nothing is continued or re-messaged, and no prompt carries a prior round's transcript, a prior maker's output, or another checker's verdict.
  • Prompts carry paths, not bodies. Artifacts move between steps through disk; the engine holds only paths, scores and defects.
  • A defect without quoted evidence is discarded, and the engine says how many it dropped.
  • The queue lives in issues/. The Blocked by: lines are the single source of truth for branch topology; no downstream document may assert an edge they do not carry.
  • The default branch is never moved, merged into, rebased onto or pushed.

When it stops before it starts

It saysFix
Running a superseded engineRestart Claude Code. Nothing else picks up the new plugin root — the run would otherwise succeed and report verdicts measured against the wrong engine.
The agents are not installedRe-run the installer, then restart. Running the graph against globally-installed lookalikes from another harness would break sdlc2's independence, so it refuses instead.
No test commandAdd commands.test. Without it the tester has no oracle and the build gate is theatre.
The baseline is redFix your suite first. Every tester verdict after a red baseline is meaningless.
The tree is dirtyCommit or stash. Slices commit, and stray changes would land inside them.
Leftover worktreesThey fail the clean-tree check and hold branches that cannot be checked out elsewhere. Release them; releasing never deletes the branch, because the branches are the deliverable.
Slices built sequentiallyNot an error — you have no commands.install. One config line shortens every future run.
The Workflow tool is unavailableStop. There is no fallback engine in 0.1, and improvising one is not a supported path.
